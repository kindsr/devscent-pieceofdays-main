## 1. 목적별 요구

| 목적 | 필요한 것 |
|---|---|
| 기록(MVP) | 서버 렌더 + 폼 저장, 로그인 세션, 소유권 검사, 한국어 본문 렌더 |
| 원장·구매 | 단일 DB 트랜잭션, 유일·CHECK 제약, 행 잠금, append-only |
| 꾸미기 편집기 | 브라우저에서 그림 끌기·크기·회전, 슬롯 안전 영역 표시 |
| 장식 보기 | 기록 텍스트는 실제 DOM 텍스트로(접근성·사용자 폰트), 장식만 위에/뒤에 |
| 이미지 | 사진·에셋 분리 저장, 업로드 재인코딩 |

## 2. 두 후보

### A안 [추천] TypeScript + React / Next.js 서버 기능 + PostgreSQL 18 + 서비스 전용 이미지 저장소

- 앱: Next.js(App Router). 공식 문서 기준 React로 풀스택 웹 앱을 만드는 프레임워크이며 App Router는 Server Components를 지원한다. 저장·구매는 서버 측 처리(서버 함수/라우트 처리기)에서 DB 트랜잭션으로.
- 편집기 드로잉 레이어: react-konva. 공식 문서 기준 "React canvas library for drawing complex 2D graphics"이고 **브라우저 전용**이며, react-konva 메이저 버전은 React 메이저 버전과 맞춰야 한다. 따라서 편집기 컴포넌트는 클라이언트 전용으로 분리한다(서버 렌더에서 불러오지 않음).
- 장점: React 생태계와 Konva 공식 React 바인딩이 그대로 맞물림. 자료·채용 풀이 넓음.
- 단점: 프레임워크 규모가 크고 서버/클라이언트 경계 규칙을 익혀야 함. 메이저 업그레이드 주기에 따른 유지 부담.

### B안 [대안] TypeScript + SvelteKit 서버 기능 + 동일 DB/저장소

- 앱: SvelteKit. 공식 소개 기준 Svelte로 웹 앱을 만드는 프레임워크로 라우터, SSR·CSR·사전 렌더를 구간별로 설정할 수 있다. 서버 측 저장 처리(폼 액션 등)는 구현 시 공식 문서로 확인한다.
- 편집기 드로잉 레이어: Konva를 직접 사용(편집기 컴포넌트 안에서 브라우저 전용으로 생성). Svelte용 바인딩 채택 여부는 유지 상태·라이선스 확인 후 결정 [미확인].
- 장점: 번들이 작고 코드가 짧은 편, 폼 중심 화면(기록 CRUD)에 단순.
- 단점: React보다 생태계·예제가 적음. Konva 연동은 직접 감싸는 코드가 더 필요.

### 공통

- DB: PostgreSQL 18, **dev·운영 DB 분리**. 원장·구매 규칙은 DB 제약으로도 지킨다(공식 문서: UNIQUE 제약은 유일 B-tree 인덱스를 만들고, 일부 행만의 유일성은 부분 유일 인덱스로, CHECK는 다른 행·테이블을 참조할 수 없으므로 행 간 규칙은 UNIQUE·FK·트리거로). 예: `grant_key UNIQUE`, `Entitlement UNIQUE(buyer_id, listing_id)`, `CreditAccount CHECK (balance >= 0)`, 외래키. 외래키는 참조 측 인덱스를 자동 생성하지 않으므로 직접 만든다.
- 이미지: 기존 S3 호환 저장소(S3/MinIO)에 **이 서비스 전용 버킷**, 기록 사진과 장식 에셋은 접두어·권한 분리. 업로드 재인코딩 라이브러리는 구현 시 선택.
- 생략 권고(공통 docs/10, 메인 전달): 별도 Python 서버, Redis, 메시지 브로커. 필요가 생기면 그때 결정 기록에 근거를 추가.
- 인증 방식·라이브러리는 [미정] (PLAN G4).

## 3. 라이브러리 역할 구분

| 층 | 역할 | 비고 |
|---|---|---|
| TypeScript 타입 | manifest·도메인 모델의 컴파일 시점 형태 | 런타임 보장은 아님 |
| 런타임 스키마 검증 | 서버에서 manifest·입력 검증(좌표 범위, 슬롯 키) | 라이브러리는 구현 시 선택. 같은 스키마로 타입 생성 권고 |
| Canvas(Konva) | **편집기에서만** 배치 조작: 끌기·크기·회전·안전 영역 가이드 | 결과는 manifest 데이터로 저장. 캔버스 이미지를 저장하지 않음 |
| DOM/CSS 렌더러 | **보기 화면**: D 마크업 위 장식 슬롯에 `<img>` 배치 | 기록 텍스트는 DOM 그대로 → 사용자 폰트·스크린리더·선택 가능 |
| 썸네일 | 샘플 하루 + manifest를 서버/브라우저에서 렌더해 이미지 생성 | 방식은 구현 시 결정(Konva Node 렌더 또는 헤드리스 브라우저) |

보기 화면을 캔버스로 그리지 않는 이유: 텍스트 접근성·사용자 폰트·D 불변 규칙을 DOM에서 그대로 지키기 위해서다(설계 판단).

## 4. 운영 부담 비교

| 항목 | A | B |
|---|---|---|
| 실행 형태 | Node 런타임 컨테이너 1개 + DB + 저장소 | 같음(어댑터 선택 필요) |
| 업그레이드 | React·Next·react-konva 메이저 동시 맞춤 | Svelte·SvelteKit·Konva 각각 |
| 학습·자료 | 많음 | 상대적으로 적음 |
| 편집기 연동 | 공식 바인딩 | 직접 감싸기 |

두 안 모두 현 정적 dev 이미지·준비중 운영 이미지와 다른 앱 이미지가 필요하다. 배포 파이프라인 변경은 선택 후 별도 계획으로 다룬다.

## 5. 시험 방법 (두 안 공통)

- 단위: 원장 계산, manifest 검증, 폰트 허용 목록.
- 통합(실제 PostgreSQL 컨테이너): 첫 로그인 동시 N회, 동시 구매, 잔액 부족, 교착 방지 잠금 순서, 마이그레이션 적용·되돌리기.
- 브라우저(E2E): 375/768/1440px에서 D 기본 vs 장식 적용 비교, 키보드 조작, 편집기 끌기·리셋, fallback.
- 선택 전 확인 실험 [권고]: 각 안으로 "조각 1개 저장 + Konva 스티커 1개 배치 → manifest 저장 → 보기 화면 렌더"를 하루 이내 시험 구현(버리는 코드)으로 비교.
