## 1. 단계 1 — MVP

**최신 요구 반영 제안:** 사용자 폰트 설정과 첫 로그인 10개를 MVP에 넣는 것은 2026-11-02 요구에 맞춘 **제안**이다. 사용자가 빼면 각각 단계 3 직전으로 옮긴다(구조 문서 §6.2의 소급 지급 경로).

범위:

- 기록: 조각(순간) 작성·**수정**·삭제, 하루 한 줄 정리 작성·수정, 날짜별 보기(D의 오늘/모아보기/특정 날), 첫날 빈 상태.
- 계정: 로그인, 본인 기록만 접근. 모든 행에 `user_id`(소유자) 저장.
- 설정: `font_key` 선택(허용 목록 2~3개, 기록 본문에만 적용).
- 감정덩어리 최소 접점: `CreditAccount`, append-only `EmotionLedger`, 첫 로그인 지급 1종. 잔액 화면 노출은 [미정].
- 카피: 확정 문구 "개인의 일상에서 순간을 기록하고 하루를 정리하여 스토리텔링을 만들어가는 감정정리 장소, pieceofdays".
- 꾸미기 대비: `Preferences.applied_design` 칸만 두고 항상 `null`(기본 D). 마켓·꾸미기 코드는 만들지 않는다.

수용 기준:

- [ ] 조각을 저장하면 시각과 함께 오늘 목록에 즉시 보이고, 수정·삭제 결과가 새로고침 뒤에도 유지된다.
- [ ] 다른 사용자의 조각·하루 정리 ID로 읽기/수정/삭제를 요청하면 거부된다(존재 여부도 드러내지 않음).
- [ ] 폰트를 바꾸면 조각 글·한 줄·입력란만 바뀌고 상단·탭·버튼·날짜 제목은 그대로다. 허용 목록 밖 값은 저장되지 않는다.
- [ ] 첫 로그인 사용자의 원장에 `first_login_grant` +10이 정확히 1행 생긴다.
- [ ] D 기준 375/768/1440px 수평 넘침 없음, 터치 대상 약 44px, 키보드 조작, 대비 AA.

TDD 필수 경계(테스트를 먼저 쓴다):

- 소유권 검사(모든 기록 조회·변경 경로).
- 첫 로그인 지급 멱등: 같은 사용자 로그인 처리를 **동시에 N회**(실제 DB, 병렬 연결) 실행해도 원장 1행·잔액 10.
- 원장 불변: 원장 행 UPDATE/DELETE 경로가 없음, 잔액 사본 = `SUM(delta)`.
- `font_key` 허용 목록 검증.

실패 사례(테스트 포함): 로그인 콜백 중복, 두 기기 동시 첫 로그인, 지급 트랜잭션 중간 실패(원장·잔액 둘 다 없음), 수정 중 다른 탭에서 삭제된 조각, 허용되지 않은 폰트 키.

마이그레이션·복귀: 첫 스키마 생성. 배포 전 dev DB에서 적용→되돌리기→재적용 확인. 운영 DB는 dev와 분리. 원장 테이블은 되돌리기 시에도 데이터를 지우지 않는 방향(백업 후 진행)으로 절차를 둔다.

비목표: 사진 외 미디어, AI 초안(PRD §7 결정 전), 공유, 꾸미기·마켓, 감정 통계.

## 2. 단계 2 — 하루 꾸미기 편집기

의존: 단계 1, 이미지 저장소(서비스 전용 버킷), 업로드 검증·저작권 정책 초안([미정] 해소 필요).

범위: 에셋 업로드·검증, 슬롯 v1 5종 배치 편집, manifest 저장·버전, 본인 적용·리셋, 샘플 하루 미리보기. 판매 없음.

수용 기준:

- [ ] 장식을 적용해도 D의 레이아웃·색 토큰·UI 서체·터치 대상·focus 순서가 기본 D와 같다(시각 비교 + 접근성 트리 비교).
- [ ] 장식이 텍스트 상자·버튼과 겹치지 않는다(375/768/1440px).
- [ ] 미리보기·썸네일은 샘플 하루만 렌더한다.
- [ ] manifest·에셋 오류 시 기본 D로 렌더되고 기록 기능은 정상이다.
- [ ] "기본으로 되돌리기" 한 번으로 기본 D.

TDD 필수 경계: manifest 스키마 검증(범위 밖 좌표·모르는 슬롯·남의 에셋), 업로드 검증(확장자 위조, 과대 해상도, 메타데이터 제거), 렌더러 fallback, 썸네일 입력에 기록 데이터 경로 없음.

실패 사례: 위조 PNG, 거대 이미지, 삭제된 에셋 참조, 이전 `schema` manifest, 기기 폭 경계값.

마이그레이션·복귀: 꾸미기 테이블 추가만(기록 테이블 변경 없음). 기능 끄기 시 `applied_design`을 무시하고 기본 D로 렌더 → 데이터 보존한 채 즉시 복귀.

비목표: 사용자 HTML/CSS/JS, 색 토큰 변경, 날짜별 다른 디자인, 애니메이션 스티커.

## 3. 단계 3 — 마켓 + 1개 구매 + 제작자 적립

의존: 단계 2, 미정 정책 결정(제작자 지급 조건, 판매 중단 후 사용, 신고·검수, 환불·탈퇴).

범위: 게시(버전 고정), 목록·상세(샘플 하루 미리보기), 구매(구조 문서 §6.3), 보유 목록·적용, 제작자 적립 표시. 단계 1에서 원장을 넣지 않았다면 이 단계 마이그레이션에서 소급 지급.

수용 기준:

- [ ] 구매 1건에 구매자 −1, 제작자 +1, `Purchase`·`Entitlement` 각 1행이 한 트랜잭션으로 생긴다.
- [ ] 같은 구매 요청 재시도·더블클릭은 결과 1건이다.
- [ ] 이미 보유한 디자인·본인 디자인은 차감 없이 적용된다.
- [ ] 잔액 0에서 구매하면 아무 행도 생기지 않고 부족 안내가 나온다.
- [ ] 재적용·미리보기·버전 갱신은 원장을 바꾸지 않는다.

TDD 필수 경계: 구매 트랜잭션 전체(실제 DB). 동시성: 잔액 1인 사용자의 서로 다른 디자인 동시 구매 2건 → 1건만 성공, 같은 디자인 동시 구매 → 권리 1행, 두 사용자가 서로의 디자인을 동시에 구매 → 교착 없음.

실패 사례: 제작자 +1 삽입 실패(전체 롤백), 판매 중단 직후 구매, 탈퇴한 제작자, 원장·잔액 사본 불일치 감지.

마이그레이션·복귀: 마켓 테이블 추가, 소급 지급은 `grant_key` 유일 제약으로 재실행 안전. 문제 시 마켓 화면·구매 경로만 끄고 원장은 보존(정정은 반대 부호 행).

비목표: 현금 충전·환전, 가격 차등, 리뷰·랭킹·소셜.

## 4. 단계 4 — 추가 사용처 [미정]

감정덩어리의 다른 사용처가 정해지면 `reason`을 추가하고 단계 3의 트랜잭션 패턴(잠금 순서·멱등 키·잔액 검사)을 재사용한다. 사용처가 정해지기 전에는 설계하지 않는다.

## 5. 검증 공통

- 단위·통합 테스트는 PR 검사에서 실행. 원장·구매·지급의 동시성 테스트는 모의 객체가 아닌 실제 DB 컨테이너로.
- 화면: 375/768/1440px 브라우저 확인, 키보드·스크린리더 기본 점검, 장식 적용 전후 비교.
- 배포·운영 확인은 메인 통합 단계에서 기존 dev→main 절차를 따른다(이 계획은 배포 경로를 바꾸지 않는다).
