- 기준: `dev` `690be1d54eaa990f7bce8198690669cf8c064b71`. 제품·DB·서버·배포 변경은 없다.

- 시간 확인(2026-11-10): "설정된 시간은 사용자 메뉴에서 설정을 통해 회고하는 시간을 사용자가 설정하는 시간을 말하는건데, 기본적으로 저녁8시쯤으로 세팅하면 좋을 듯하고. 설계에 있지 않나". **사용자 메뉴의 설정에서 일일 회고 시각을 바꾸며, 초기 기본값은20:00이다.**
- 이 확인은 기존 "글만 저장 → 직접 정리 우선, 사진·AI 후속" 가정을 대체한다. 사용자가 과거 AI를 포기했다고 소급해 기록하지 않는다.
- 정본: [PRD](../PRD.md)·[MVP](../product/03_MVP.md)·[스토리보드](../product/04_STORYBOARD.md)·[D 핸드오프](../design/README.md).

## 1. 확정과 확인할 세부

| 항목 | 현재 판단 |
|---|---|
| 핵심 경험 | **[확정]** 사진·짧은 메모·시간을 바탕으로 하루를 회고하고 AI가 하루의 이야기를 만든다 |
| 기기 | **[확정]** PC·휴대폰 모두. 같은 계정의 원본과 이야기를 다른 기기에서 다시 불러온다 |
| 사진 | **[확정]** 실제 사용자 사진 입력. 예시 SVG로 대체하지 않는다. 장수·크기·필수 입력 조합은 세부 설계에서 정한다 |
| 직접 쓴 한 줄 | 기존 보조 기록으로 보존할 수 있지만 AI 하루 이야기를 대신한 완료 기준이 될 수 없다 |
| 회고 시간 | **[확정]** 사용자 메뉴 → 설정에서 일일 회고 시각 선택·변경. 초기 기본값20:00(저녁8시). 개별 사진·메모의 기록 시각을 입력/수정하는 요구와 구분한다 |
| AI 전송·운영 | **[미정]** 제공자/모델·외부 전송 동의·사진 분석 범위·보관·비용 한도. AI 채택과 특정 외부 업체로 실제 일기를 보내는 결정은 구분한다 |
| 공유·마켓 | 기존 후속/미정 범위 유지. 이야기를 자동 공개하지 않는다 |

## 2. 실제 구현 공백

| 기능 | 기준 소스 상태 |
|---|---|
| 짧은 메모 | 계정별 CRUD·서버 저장·날짜별 읽기 구현 |
| 사진 | fixture 예시 키3개, PG 읽기는 `image: null`. 실제 업로드·사진 저장 관계 없음 |
| 시각 | 기준 dev에는 서버 기록 시각·서울 날짜·시간순 목록만 존재. PR81에서 사용자 메뉴의 회고 시간 기본20:00·계정 저장을 구현·CI 검증 중(서비스 DB/게시 전) |
| 하루 정리 | 사용자가 직접 쓰는300자 한 줄 |
| AI | 생성 모듈/실제 호출·생성 상태·이야기 저장 모델 없음 |

로그인·저장·권한·기기 검사는 재사용할 기반이다. 기술 배포 성공과 제품의 핵심 경험 완성은 별도로 보고한다. 현재 dev는 실로그인 검증 미완료 뒤 정적 화면으로 복귀한 상태다. 회고 시각은 하루를 돌아보는 기준이며 조각의 저장/발생 시각을20:00으로 덮어쓰거나 새 시간 입력을 강제하지 않는다.

## 3. 끝까지 이어야 할 사용자 흐름

다음은 핵심 요구를 잇는 **구현 제안**이다. 회고 시각과 기본20:00은 확정이며, 정시 자동 생성/알림 전달의 구현 방식은 별도 설계한다.

1. 사용자 메뉴 → 설정의 ‘회고 시간’에서 기본20:00을 확인하고 원하는 시각으로 바꾼다. **[제안]** 계정에 저장해 PC·휴대폰에서 같은 값을 다시 불러온다.
2. 실제 사진·짧은 메모로 조각을 남기고 설정한 회고 시각에 하루를 돌아본다. 원본과 AI 결과를 구분한다.
3. AI가 그날의 사진·메모를 연결한 하나의 이야기를 만든다. 생성 중·입력 없음·실패 상태를 표시한다. 실제 호출 없이 성공을 보여 주지 않는다.
4. 생성된 이야기를 사진·원본과 함께 읽고 저장해 날짜별로 다시 연다. **[제안]** 사용자 수정·재생성은 이미 수정한 글이나 원본을 자동 덮어쓰지 않도록 별도 버전으로 다룬다.
5. 다른 기기에서 같은 날짜의 원본과 저장된 이야기를 다시 읽는다.

## 4. 구현 단계·변경 경계 초안

구체 API/파일/migration 이름은 각 단계 RED 전에 정한다. 새 프레임워크·큐·AI 공급자를 이 문서로 확정하지 않는다.

| 순서 | 대상·산출물 | 먼저 정할 것 |
|---|---|---|
| 요구·화면 | PRD/분석/MVP/스토리보드/핸드오프. D 조각 입력·회고 시간 설정에서 이야기 읽기까지 실제 화면 설계 | 설정 진입·기본20:00·변경 상태 포함 |
| 사진 입력·보관 | `app/src/app/` 업로드 경로·서버 사진 모듈·소유권·기록 DTO·신규 migration/시험 | 전용 비공개 저장소 세부, 형식/크기·보관/삭제 |
| 회고 시간 설정 | 사용자 메뉴의 설정 UI·계정 저장 모델·기본20:00·시각 변경. 기존 조각 생성 시각과 분리 | 현행 기록 시간대 정책과의 표시·저장 기준을 구현 설계에서 명시 |
| AI 하루 이야기 | 서버 전용 생성·입력 묶음·결과 저장·실패 상태·읽기 화면 | 제공자/전송/비용·품질 기준. 실제 일기 호출은 해당 조건 확인 후 |
| 정시 회고 동작 | 사용자별 회고 시각과 생성·안내 동작의 연결 | 자동 AI 호출·알림 채널·중복 방지의 구현 방식을 별도 설계. 시간 설정 확인만으로 서버 예약 작업이나 외부 전송을 켜지 않음 |
| 통합 검증 | 실제 사진→메모/시간→AI 생성→보관→PC/휴대폰 다시 읽기 | mock/실제 공급자/실기기 결과 구분 |

기존 인증·소유권·동시 수정·글꼴은 재사용한다. 꾸미기 확정 요구·마켓 후속 정책을 삭제하지 않는다. 새 사진/이야기에도 계정 탈퇴·복구·삭제 정책을 적용하도록 설계를 포함한다.

## 5. 제품 핵심 완료 기준

- [ ] 예시가 아닌 실제 사진을 올리고 다시 불러온다. 타인의 사진을 읽거나 붙일 수 없다.
- [ ] 사진·짧은 메모가 같은 하루에 연결되고 PC·휴대폰에서 확인된다.
- [ ] 사용자 메뉴 → 설정에서 회고 시간 기본20:00을 표시하고 사용자가 바꿀 수 있다. **[제안 검증]** 저장·재접속·같은 계정의 PC/휴대폰 재조회가 일치한다.
- [ ] 회고 시각과 조각 기록 시각을 구분하고, 정한 시각의 회고 경험·빈 날·실패 처리를 검증한다. 자동 생성·알림을 채택하면 해당 실행도 별도 검증한다.
- [ ] 실제 AI가 그날 입력을 바탕으로 이야기를 만든다. 입력에 없는 사건·인물·대화·감정을 사실로 지어내지 않는지 평가한다.
- [ ] 저장한 이야기를 다시 읽고 원본과 생성/수정 결과를 구분한다. 수정·재생성은 확정된 계약을 따른다.
- [ ] 실패해도 원본과 이미 저장한 이야기는 보존된다. 입력 변경·중복 요청·계정 변경 중 생성의 처리 기준을 검증한다.
- [ ] 사진·이야기의 계정 간 접근 거부, 로그/공개 노출 방지와 승인한 전송 범위를 검증한다.
- [ ] 기존 메모 CRUD·달력·글꼴·기기별 세션·소유권 회귀를 통과한다.

기존 root108·구조128·auth35·DB178 등은 기반 기능의 증거이며 위 사진/AI 핵심 흐름의 완료 증거로 대신하지 않는다.

## 6. 검증·복귀

- 최초 요구 정렬은 문서만 변경했다. 후속 PR81의 회고 시간 제품/SQL/시험 변경은 [전용 계획](PLAN_reflection-time-settings.md)을 따르고, [비공개 사진 후속 계획](PLAN_private-photo-moments.md)은 아직 준비 단계다. 실제 저장소·AI 호출·예약 실행·서버·배포 설정은 변경하지 않으며 dev push/자동배포 보류를 유지한다.
- 문서는 최신 사용자 요구/과거 가정·실제 구현 여부·용어·링크를 대조한다. 앱/DB 시험은 문서 수정만으로 새로 실행하지 않는다.
- 구현 때 소유권·파일 검증·전송/비용·시간·중복 생성의 위험 경계를 RED→GREEN으로 분리한다.
- **복귀 제안:** 각 기능을 중단해도 기존 메모·사진·완성 이야기를 삭제하지 않도록 나눈다. migration/객체 삭제/외부 AI 전송의 복귀 계약은 구현 전에 쓴다. 외부로 이미 보낸 내용을 코드 revert로 회수할 수 있다고 약속하지 않는다.
